# 需求入选规则

GRM AI 自动化值守 · 第二期｜确认日期：2026-10-14｜流程版本 v5

> 🎯 **每周把 Grooming 团队承接的用户反馈变成可决策、可实施的事项。**需要产品/设计决定的生成决策卡，等真人决定后自动实施；做法已由现有产品决定的直接实施。决策卡是主要产出，没有合格候选时允许不选，不为凑数降低标准。

## 1. 输入与范围

- 输入：Asia/Shanghai 上一个完整自然周已发布的 Canny、Intercom、Jira、Facebook 四源明细，跨月周合并全部片段。来源未发布时等待，不用旧周替代。
- 范围：**只入选 Grooming 团队承接的问题。**其它团队承接的问题（如订金、收据、支付、报表平台）不入选、不生成决策卡，在候选页记录归属与依据。归属查不清的不入选。
- 客户报告的代码 Bug 主要由每日 Bug 值守处理；已有在途的每日值守、Bug Resolver、Jira 或 PR 只关联，不重复开工。周值守核实中发现、且无人处理的缺陷，按直接实施入选。

## 2. 出卡前核实

拟入选的问题先只读核实三件事，结论写入候选页：

| 核实项 | 结果 | 处理 |
|-|-|-|
| 是否 Grooming 承接 | 否 | 不入选 |
| 功能是否已存在 | 已存在 | 不入选，建议客服引导 |
| 现行为是否违背已有规则或已上线行为 | 违背 | 按缺陷直接实施 |

查不清且影响分类的，保留为“待补证”，不入选，也不交给产品猜。

## 3. 三类入选项

| 类型 | 判断标准 | 产品/设计要做什么 |
|-|-|-|
| 直接实施 | 核实为缺陷，或做法已由现有产品决定：照搬同一产品已有样式、往已有清单加项、新场景沿用已有状态含义、补齐另一端已有能力 | 不需要参与，交付后审查 |
| 待确认卡 | 需要产品/设计确认，但只有一类诉求，AI 能给出无明显受损方的推荐 | 看推荐的范围与验收标准，可直接回复“同意推荐” |
| 待取舍卡 | 同期出现诉求相反的用户群，任何选项都会让一方受损 | 判断优先照顾谁、放弃什么 |

## 4. 名额与排序

- 每周最多新入选 5 项，包含三类；不足不凑数。
- 未决的待取舍卡（含往期）合计不超过 2 张，已满时新的取舍候选下周重新评估。
- 按用户价值排序：频繁发生、多个独立用户或渠道提出、明显妨碍操作或造成流失。vote≥5 和跨渠道提出是优先信号，但票数只是证据，不等于实施批准。价值接近时选交付成本更低者。
- 往期未决卡沿用原任务，不占新名额，有新证据才更新。

## 5. 决策卡

每张卡使用七项结构：问题与来源、用户背景、现状与依据、这次需要决定什么、决策选项、AI 推荐、人工决定与执行边界。只写已核实事实，缺口写明已查内容。待确认卡的 AI 推荐须写全范围、不做什么、验收标准和参照的现有实现。

真人在对应 Multica 问题任务 @GRM AI 自动化值守小队 回复决定后，小队自动接续实施。“方向不错”“可以考虑”不作为实施批准；暂缓、不做也是有效决定，会记录理由和再评估条件。

## 6. 交付

每项实施由同一工程 Agent 完成开发、实际验收、修复复验、PR 和完整 HTML 验收报告，交付到指定 Slack 频道等待审查。交付不代表 PR 合并或生产发布。
